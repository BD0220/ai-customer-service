# ai-customer-service 专业化升级任务清单

> 参照对象：DevFlow-AI（通用机制层：契约/引用/阈值/评测/可Observability）+ Chatwoot（产品形态层：三级接管/收件箱/质检）+ MewHelp（小林coding 同领域付费课程项目的公开设计点：引用/置信度闸门/断点续传/Workflow 混合）。
> 背景：2026-10-16 已完成 Chatwoot 式人工接管（会话 mode + 坐席工作台），那是产品形态层的第一块；
> 本清单补完剩余部分。原则与 abundance 清单相同：只移植机制，不追广度；每条对应一个真实场景或面试题。
> 状态：待用户审阅。确认后按 P0 → P1 执行，每项完成跑评测回归 + 单独提交。

## P0 必做（答案质量底线，约 1.5 天）

### C1 证据链：回复带引用（0.5 天）
- **做什么**：`rag_engine.format_context` 已返回来源字段，提示词要求回答标注依据（“根据《退换货政策》第 3 条”）；无 KB 命中时明确说“知识库未覆盖，已转人工/建议核实”，不允许硬答；评测加“引用存在性”断言。
- **治什么**：客服场景答错要担责——没有引用的答案不可审计、不可复盘。DevFlow 的 citations 机制同款。
- **面试点**：“客服 LLM 怎么防幻觉”——检索命中才答、没命中就说没有，答案永远挂得到原文。

### C2 置信度阈值自动转人工（0.5 天）
- **做什么**：Agent 输出信封带 `confidence`（依赖 C3）；`confidence < 阈值` 或 KB 无命中或工具结果异常 → 直接走转人工，不再尝试硬答。现有三层转人工（关键词/Agent 调工具/异常兜底）升级为四层。
- **治什么**：现在转人工靠“模型自己觉得该转”，没有量化闸门；低置信度硬答是客诉的主要来源。
- **DevFlow 出处**：confidence < 0.45 阈值触发 replan——同款机制的转人工版本。
- **依赖**：C3。

### C3 结构化应答契约（0.5 天）
- **做什么**：定义应答信封 `{reply, intent, confidence, sources[], actions_taken[], need_human, ticket_id}`；`customer_service_agent.py` 解析信封；去掉现在把 `tool_trace` 文本拼进回复的 hack（调试信息进数据结构，不进用户可见文本）；评测直接断言信封字段。
- **治什么**：自由文本回复=评测只能关键词匹配、审计只能靠人读；信封化后意图/置信度/动作全部可机器断言。
- **DevFlow 出处**：全仓 pydantic 类型化（与 abundance T1 同一机制，可互相参照实现）。

## P1 选做（叙事与深度，约 3.5 天）

### C4 评测深化（0.5–1 天）
- **做什么**：现有 5 项指标加**分意图（category）维度**（退款/物流/投诉各类分别出准确率，不再只有一个总数）；加**失败归因**（模型波动/提示词/检索未命中/工具异常）；同用例集两次跑批自动对比；补 **5–8 条多轮会话用例**（现有 20 条全是单轮，没有上下文继承场景）。
- **为什么**：从“20 用例三项 100%”升级为“分意图 100% + 失败可归因 + 版本间可回归”——后者才像生产系统的评测。
- **DevFlow 出处**：evals/suites + 归因 + 回归对比。

### C5 接管深化：Copilot 中间态（1 天）
- **做什么**：接管从二级（ai/human）扩为三级——**auto（AI 直接回）/ copilot（AI 拟稿，坐席修改后发送）/ human（纯人工）**；坐席工作台在 copilot 态显示 AI 建议草稿；接管时自动生成交接摘要（用户意图/情绪/待办/已尝试方案）随会话递给坐席；会话关闭后落一条质量记录（是否解决/响应时长/是否二次转人工）。
- **为什么**：Chatwoot Captain 的标准三级；copilot 态是“AI 产能 + 人工把关”的性价比最优点，也是面试讲 HITL 分级的现成素材。
- **Chatwoot 出处**：auto → copilot → human 分级处理。

### C6 可观测性（0.5 天）
- **做什么**：会话级 trace 落库（每轮：工具调用/token/延迟/转人工决策及原因）；工作台加简单的会话审计视图。
- **为什么**：“客服质量怎么审计”“为什么这句话转人工了”这类运营问题的现成答案；DevFlow agent_events 同款。

### C7 RAG 升级 TF-IDF → 向量检索（1 天）
- **做什么**：`rag_engine.py` 的 `BaseRetriever` 抽象就是为这个预留的——新增 `EmbeddingRetriever`（ChromaDB 或本地 sentence-transformers），TF-IDF 保留为兜底与对照；用 C4 的评测集跑两版检索对比（通过率/引用命中率），用数据证明升级有效。
- **为什么**：TF-IDF 对同义改写无力（“啥时候能到” vs “配送时效”）；且“用评测数据驱动检索升级”本身是强叙事。abundance 已走完同款路（单路向量 + 砍重排），可参照。
- **验收**：同义词用例两版通过率对比，向量版不劣于 TF-IDF 且同义句明显改善。

### C8 长会话上下文压缩（0.5 天）
- **做什么**：超过 N 轮后对早期历史做摘要压缩再喂 LLM（保留最近 K 轮原文）；压缩点落库可查。
- **治什么**：现在 20 条硬截—— customer 唠叨 30 轮后 AI 忘了开头说过什么。
- **DevFlow 出处**：progressive compaction。

### C9 断点续传：缺关键信息不猜（0.5 天）
- **做什么**：缺少关键参数（如订单号）且无法从上下文推断时，Agent 不猜——暂停当前流程向用户追问/弹出选择，用户补充后从断点继续（LangGraph `interrupt` / `Command(resume)` 标准用法），已执行的步骤不重跑。
- **治什么**：现在缺信息时模型倾向编一个订单号继续跑，**查到错数据比不查更糟**。
- **MewHelp 出处**：同款场景——"无法确定是哪一笔订单时，系统会暂停流程，让用户选择订单，再从断点继续处理"。
- **面试点**：“LangGraph 的 interrupt 怎么用”“人机协同的断点恢复怎么做”。

### C10 Workflow + Agent 混合架构（架构级，可选，1–2 天）
- **做什么**：把高风险、规则明确的多步操作（退款：验证订单→核对政策→确认金额→执行→留痕）编码为确定性 Workflow（步骤固定、每步可校验、全程可审计）；开放问答和意图判断继续走 Agent；入口处路由分流。
- **为什么**：纯 Agent 跑高风险流程，每一步都是模型自由发挥，出错不可控也不可审计。MewHelp 的核心设计——“明确规则和高风险业务交给 Workflow，需要判断和调用工具的任务交给 Agent，既保留 AI 灵活性又不突破业务边界”。这是"AI 应用落地"与"Agent demo"的分水岭叙事。
- **注意**：本清单改动最大的一项，依赖 C3 契约先落地；C1-C9 完成后仍有余力再上。

## 明确不做（及理由）

| 不做的 | 理由 |
|---|---|
| 多 Agent 编排 | 客服单 Agent 是正确形态；拆多个角色是过度设计，面试是负分 |
| DAG / 异步并行 | 对话严格串行，无可并行分支（与 abundance 同结论） |
| 多渠道统一收件箱 | Chatwoot 的核心，但你没有真实渠道接入，做了没有数据流 |
| MCP / 知识图谱 | 生态广度非深度 |
| 登录鉴权 | 单机自用，已决议免登录 |

## 简历联动

C1+C2+C4 落地后，客服项目简介可加：“答案 100% 带知识库引用、低置信度自动转人工、分意图评测 + 失败归因”——把现在的“三项 100%”升级为可归因、可回归的质量证据链。人工接管 + Copilot 三级则是 HITL 分级的完整故事（流程闸门 / 会话接管 / 拟稿协作，三种模式横跨两个项目）。
